# Changelog

## 1.1.0 (2026-07-15)

- **Map: fixed a performance regression that built up the more saves you loaded.** The Map tab's two static assets (the 16384x8192 location-id grid and the location name/color table) were being re-fetched and re-decoded from scratch on every single save load instead of once per page load. Each of those was close to ~1GB of transient allocations, so loading several saves in one session left the heap full of not-yet-collected garbage, and pan/zoom (which re-renders on every frame while dragging) would visibly drop frames as a result. They're now cached after the first load and reused for every save after that - this was the dominant cost. A smaller, separate memory-growth pattern across saves with genuinely different content is still being tracked down as a follow-up.
- **Map: added missing units to location detail popups.** Numbers in the location click-through popup were often shown with no indication of scale (e.g. an Estate Tax breakdown value like `50.9123` with nothing saying what it meant). Fixed:
  - The Estate Tax and Institutions tables had no column headers at all - added them (`Estate` / `Tax Base`, `Institution` / `Progress`).
  - Institution progress values now show as a percentage (e.g. `100%`) instead of a bare number; a fully-embraced institution (stored as the string `"yes"` rather than a number) no longer renders as `NaN`.
  - "Weighted Tax / 1k People" and "Total Group Tax" now carry the same `tax` unit suffix as the sibling Tax Base stat.
  - "Raw Material Capacity" now reads e.g. `1 RGO capacity` instead of a bare `1`.
- **Map: moved rendering from the CPU to the GPU (WebGL2).** Panning/zooming the map used to visibly spike CPU usage and spin up fans, even on fast machines - the old renderer recomputed every visible pixel (fill color, box-average downsampling once zoomed out, border/coastline detection, selection highlight) in a plain JS loop, on the main thread, on every single animation frame. That's now a WebGL2 fragment shader doing the same per-pixel work in parallel on the GPU instead, which is what tools like PDX Tools do too. Falls back automatically to the old CPU renderer if WebGL2 isn't available at all. Measured: drag-frame timing while fully zoomed out went from ~22-32ms average (with spikes to 400ms) to a flat 16.67ms (60fps) with no spikes.
  - Known gap: the "control" mapmode's fragmented-ownership shading pass wasn't ported yet (everything else - political, players, development, population, tax, markets, religion, culture, prosperity, trade, selection, labels, tooltips, click-through - was verified against the old renderer). Follow-up if it turns out to matter.
  - Fixed shortly after release: player/AI realm borders were rendering as a single GPU pixel, which is visually indistinguishable from the ordinary thin location-boundary line already drawn everywhere - so multiplayer nation borders looked like they'd disappeared entirely. The CPU renderer thickens this same edge into a several-pixel-wide line; the GPU version now does the same (checks a small neighborhood around each pixel for a realm change, not just the immediate neighbor), confirmed against the CPU renderer on a real multiplayer save with 8 player nations. Also fixed a real, independent bug found in the process: coastline shading was reading a location's own "is this a sea tile" flag through an inverted water check that made it always resolve to false.
- **Map: population/tax/development gradients now color by percentile rank instead of any value-based scale.** First tried a log scale (better than the original linear min→max, which crammed nearly every location into the same dark color), but a side-by-side against a PDX Tools screenshot of the same save/region showed ours still reading mostly one color - these fields stay right-skewed even in log space. Coloring by each location's *rank* among its scope's locations instead of its raw value is invariant to that skew entirely (by construction, colors always spread evenly across the full gradient, no matter how lopsided the underlying numbers are) - this is the standard "quantile classification" technique cartographers use for exactly this kind of data, and is almost certainly what PDX Tools is doing too. Confirmed a real, even green→yellow→orange→brown spread on the same region PDX Tools was screenshotted at.
- **Investigated: a specific save shows prosperity as a single flat color.** Root-caused - that save has only 3 locations (out of ~13,000+) with any recorded prosperity value at all, vs. 12,000+ for control/tax/development. Missing values currently get filled in as an explicit 0 for any owned location that has other data, so with so few real data points, everyone's identical "0" ends up anchoring one end of the whole gradient. Looks like an early-game save where prosperity genuinely hasn't diverged anywhere yet, not a parsing bug. Not yet fixed - candidate fix is falling back to "no data" gray instead of a fabricated 0 when a field's real data is this sparse.
- **Map: replaced the heat gradient with a richer multi-hue ramp** (green → olive → gold → orange → dark red-brown), matching the ColorBrewer "sequential multi-hue" family (the YlOrBr/YlOrRd style) that PDX Tools also uses for province heatmaps. The previous dark-brown → tan → green ramp read as muddy/low-contrast across the middle of the range - a single-hue ramp doesn't carry enough visually-distinct steps for a full map legend, especially with population/tax now log-scaled. Adjacent-step contrast checked with the dataviz skill's palette validator.
- Fixed shortly after release: the new multi-hue ramp above shipped with low/high reversed (green at 0, brown at the max) - the original convention was the other way around (dark at 0, green at the max, per the "floor color" note in the code). Same five colors, just flipped back to the original direction.
- **Map: heat gradient (development/population/tax/control/prosperity) recolored again, this time to dark brown → yellow → green → bright cyan-blue**, per user sign-off against a PDX Tools screenshot. The previous brown/orange/gold/olive/green ramp had a real defect independent of hue choice: measured luminance showed it peaking in brightness at the gold stop (~75% up the scale) then getting darker again for olive/green - the brightest color on the map was never the highest value. The new ramp's floor is a dark chocolate-brown rather than literal black, for the same reason as before: true black reads as identical to the page's own background/`NON_PLAYER_MUTED`, which would make a genuine 0% location indistinguishable from "nothing rendered here." Percentile-rank scaling (unchanged) still does the actual work of spreading real save data evenly across the gradient regardless of skew - confirmed with a simulated right-skewed dataset that linear scaling crowds 92% of locations into the darkest quarter of the gradient, log scaling still crowds 29%, percentile rank spreads it exactly evenly (25% in each quarter).
- **Map: heat gradient's control points are now spaced unevenly across percentile-rank space instead of evenly.** Originally: bottom 30% brown/near-black, next 25% (30-55th percentile) yellow, next 40% (55-95th) green, top 5% bright cyan-blue - a hard-edged classed/flat-band version of this was tried first (confirmed on a real save), then changed back to a smooth blend between those same anchor points per follow-up feedback, so within-band relative ranking (a 60th vs. 90th percentile location) is visible again. Re-tuned once more against a reference screenshot to compress brown/yellow into the bottom ~40% and stretch green/blue across the remaining ~60% (was ~70%/~30%) - green is now the dominant color across most of a real save's landmass, with blue visibly present rather than a rare accent. Then pulled blue back to only the true top 1% of locations (an "elite handful" flag rather than a visible band), giving the ~14 points of range that freed up to yellow (now ~29% of the range, up from ~15%) rather than green, per user request. The map legend's gradient-bar sampling was bumped from 9 to 61 points so it accurately renders a curve with unevenly-spaced control points instead of smoothing it into an evenly-spaced blend.
- **Map: removed the drag/zoom "fast" render mode** that stripped province borders and player/trade-good labels while actively panning or zooming. It was a leftover optimization from the old full-CPU renderer (skip the two most expensive passes during motion, redraw in full ~90ms after the user stops) - no longer needed now that rendering is a GPU fragment shader, so borders and labels stay on screen throughout a drag or zoom instead of flickering away and back.
- **Map: brightened the Trade Goods mapmode a little.** It was darkened from its original neon-hashed colors per earlier feedback, but ended up slightly too dark/muddy - eased the final darken step back up (was -0.16, now -0.06) while keeping the desaturation toward muted land that fixed the original neon problem.
- **Llama Score checkbox now defaults to checked** (tab visible up front) instead of waiting for auto-linked ledger data to appear before showing itself. An explicit uncheck is still remembered across sessions.
- **Map: labeled the two location-click detail panels** - the country/nation panel (left) now reads "National Stats" above its stat grid, and the location panel (right) reads "Location Stats" above its own, so it's clear at a glance which numbers describe the whole country vs. just the clicked location.
- **Map: reverted the "Painted map style" filter from earlier the same day.** Its border-thickening half worked, but the "less plastic" texture half was always going to need real hand-painted terrain art (the actual EU4 mod's source of that look) that a flat data-driven fill renderer can't fake with a shader trick alone - not worth keeping a half-working approximation. Fully removed: the `u_paintedStyle` uniform, the owner-vs-realm border key swap, the grain/desaturation shader block, the wider dilation bounds, and the checkbox UI.
- **Map: hiding a player now removes them from the map too**, not just the Players table/Trends/Llama Score. Their player-realm border, name label, and "Players" mapmode grouping/legend entry all disappear - their territory falls back to reading as ordinary AI/muted land. Works via a new `visiblePlayers()` filter in `js/map.js` threaded through every place the map reads a country's player-name list (there were about 10 of them), keyed off the same excluded-players Set the Hide/Show buttons already persisted to localStorage.
- **Hiding now also happens automatically when the desktop tracker's campaign ledger shows a player has actually left** - not just via the manual Hide button. New `LlamaScore.computeDepartedPlayers(snapshots)` reuses the existing per-country control timeline (already built for war-scoring's "player-departed" categorization) to find any player name that appears somewhere in the timeline but is absent from every country's LATEST known roster - i.e. genuinely gone, not just mid-move between countries (confirmed with synthetic timelines for both cases). `getAllExcludedPlayers()` (app.js) unions this with the manual list for every place a player should disappear from view (Players table, Trends, Map); the manual list itself stays untouched by auto-detection, so Hide/Show still only ever read/write an explicit user choice. Refreshes automatically the moment a campaign ledger links (or a live poll picks up new recorder data), not just on next reload. Known gap: the "Show all" button only clears the *manual* list - an auto-detected departed player stays hidden until they reappear in the ledger's own latest roster, which is intentional (nothing to "show" if the tracker still says they're gone) but worth knowing about.
- Bumped the site's cache-busting version string a few times as fixes landed (several JS fixes landed since the last bump under the same version each time) - if anything still looks like old behavior after pulling these changes, a hard refresh will clear it out.
