# Changelog

- **Trade Network isolate mode now greys out unconnected markets' actual territory, not just their node dot.** Per user follow-up: greying the dot wasn't enough, since the land underneath a greyed dot still showed its normal per-market color. Added `tradeNetworkFillColor` (Trade Network's own `colorFor`, separate from the shared `marketAccessFillColor` Markets mode still uses unmodified) that mutes a location's territory the same way if its market isn't in `mapState.tradeNetworkConnectedMarkets` - a single source-of-truth set now computed once per redraw by `computeTradeNetworkView()` and shared by both the land fill and the existing node-greying logic, so land and nodes can no longer show a different, disagreeing answer to "is this connected." Root-caused a real ordering bug while building this: the color LUT loop that calls `colorFor()` for every location runs BEFORE the code that used to set this shared state, so every location's color was always computed against the *previous* click's data - moved the state assignment to before the loop instead of after. **Then chased what looked like the fix still not working** through several rounds of live debug logging (confirmed the connected-set state was correct, confirmed the LUT arrays did contain the correct grey values for ~79% of locations) before finding the real explanation: it wasn't a bug at all - every verification screenshot had been zoomed into the clicked market's own immediate, real-trade-connected neighborhood, which is exactly the region that's supposed to stay in color. A zoomed-out screenshot after isolating a market confirmed the entire rest of the world's landmass renders grey while only that market's real connected neighborhood keeps its color.

- **Fixed Trade Network mode showing a broken, inconsistent view when a country was already focused from another mapmode, and added the requested "grey out everything not connected to the selected nation" behavior.** User reported land going dark almost everywhere while trade lines/nodes stayed fully colorful and seemingly unfiltered - root cause: `mapState.focusCountry` (set by clicking a country in ANY mapmode, e.g. Political, and persisting across a mode switch) already made Trade Network's land fill mute non-focused territory (via the shared `marketAccessFillColor` from an earlier fix), but the trade edges/nodes were an eagerly-computed cache that only ever updated on a Trade-Network-specific click - so a focus set from a different mapmode never touched it at all, and the two just drifted out of sync. Rearchitected the trade-network view to compute fresh every time `buildLUTs()` runs (already called on every state-changing action - a click, a focus change, a mode switch) instead of maintaining a separately-mutated cache, so it can never go stale again regardless of where the focus came from. Added the actual requested feature: when a country is focused and no specific market is isolated, the view now narrows to every market reachable via ANY chain of real trade from one of that nation's own markets (`marketsOwnedByCountry` + a breadth-first `reachableMarketSet` walk over the world trade graph - not "routes this nation's own merchants established," the same flawed, narrower interpretation already tried and reverted earlier this session) - unreachable markets grey out via the existing node-muting mechanism instead of the land-only muting from before. Verified two ways: directly against the real 1513 save's data, Eastern Rome reaches 137 of 139 active world markets via chain (including Beijing - the exact trade this whole session started from), with only 2 genuinely unreachable; and live in the browser, a country focused in Political mode and carried into Trade Network mode rendered the reachable-via-chain view without error, zero console errors across every test run.

- **Trade Network's market-isolate view now greys out unconnected markets instead of hiding them.** Per user request, clicking a market used to remove every other market's node entirely, losing the "where does this sit in the world" context. `computeMarketNodes` now always uses the full world's active-market list as its node set, with an optional highlight set (the isolated market's own routes) marking each node `connected: true/false` - the draw pass renders unconnected nodes as a dim grey circle instead of their real color, same two-pass stroke technique as the colored ones. Default world view is unaffected (no highlight set, every node stays in its own color). Verified live: default view unchanged, market-isolate view shows a mix of full-color connected nodes and greyed-out unconnected ones, zero console errors.

- **Reverted Trade Network's click-a-player-to-isolate-their-country feature, same session it shipped.** User reported market selection became unreliable and a known-real trade (Eastern Rome's Beijing-sourced porcelain, the exact route earlier verification traced hop-by-hop) had disappeared. Root cause: `route.country` (`trade_path_manager`'s own field, used to key the new per-country isolate) is whichever country's MERCHANT established a route, not who owns the market it lands in - confirmed on the real save, that Beijing->Constantinople porcelain trade was established by a different country's merchant entirely, so it never appeared in an Eastern-Rome-scoped view even though it plainly still touches Constantinople's own market. Worse, clicking anywhere inside a player's territory (which is most of the interesting map) now diverted to the country view instead of the market popup, breaking ordinary "click this market" selection. Removed `setTradeNetworkCountryIsolate`/`edgesForCountry`/`routesByCountry` entirely and reverted `showLocationDetails` to always isolate by MARKET regardless of who owns the clicked land - the mechanism that was already proven correct (it isolates by which market a route's real decomposed path starts/ends at, never by who established it, so it has no such blind spot). World-network default, market-isolate on click, and water/Escape-clears-to-world all stay exactly as shipped. Verified directly against the real save: Constantinople's market isolate includes that exact porcelain trade again (180 routes total, the Beijing one among them, 28 hops); live re-test showed zero console errors and reliable market selection.

- **Reworked Trade Network's default-view/click model per user correction, and fixed a real bug the new interaction exposed.** A prior same-session change had defaulted the mapmode to just one arbitrary player's trade (`firstPlayerCountry()`, whichever player happens to be first in the save's own player list - not necessarily "you") instead of everyone's - user clarified they actually wanted the full world network by default, with drill-down on demand: click a player's territory to isolate that country's whole trade network, click a market for just its own routes, click open water or press Escape to return to the world view. Confirmed against the real save: that exact Beijing-Constantinople line was a 0.023-unit/month porcelain trade whose 181-waypoint path decomposes (via each waypoint's own market) into a real ~28-hop chain through legitimate intermediate markets - 28 of 29 consecutive hops matched a real market-to-market trade-range connection. A user reported isolating on a market showed edges that looked completely disconnected from the rest of its network; traced to the real cause on the same save - `connectedMarkets` isn't exhaustive (a real Beijing->Athens porcelain trade's actual path visits Baghdad then Acre back-to-back, but that pair isn't listed), so the filter was silently cutting real routes into orphaned pieces. Removed the filter entirely - every hop already comes from a route's own real waypoint path, which needs no second-guessing against a separate, incomplete list. Verified directly on the real save: Beijing's isolate view goes from 46 edges (Constantinople/Acre/Athens stranded as an unreachable cluster) to 55 edges, with the entire 45-market chain now one connected component reachable from Beijing.

- **Fixed the Llama Score dashboard crashing on a real, large, actively-growing campaign.** Root-caused in three layers, each confirmed by direct reproduction against the real save rather than guessed: (1) the two-phase tape parser's transient memory use scales roughly 60-70x a save's raw byte size (measured: a real 71MB save peaked ~4.3GB) — the parsing worker now gets its own raised heap ceiling; (2) EU5's autosave rotation can overwrite several ~75MB+ slots while a session is live, and running more than one large parse at once needed 15-20GB+ simultaneously — concurrency for any file over 15MB is now hard-capped to one at a time, gated additionally by a live `os.freemem()` check before starting (the *actual* trigger for the crash turned out to be system-wide memory pressure from the real game running alongside the recorder at the same time, confirmed via live memory monitoring during a repro, not the recorder's own accounting); (3) a worker that dies without ever reporting success or failure (observed once under real memory pressure) used to leave the whole scan hung forever with no error — the recorder now treats a worker's `exit` with nothing settled as a definite failure instead of waiting on it indefinitely. A related deadlock introduced by an earlier iteration of fix (2) — deferring a file for memory reasons could leave nothing left to ever retry it — was caught and fixed the same day.

- **Rearchitected the binary parser onto a two-phase "tape" design, matching [jomini](https://github.com/rakaly/jomini) - the Rust parser PDX Tools itself is built on for EU4/EU5/CK3/HOI4/Vic3/Imperator.** The old parser did one recursive pass that decoded bytes AND interpreted their meaning at the same time, so a wrong assumption about what a section *meant* (like assuming the true top level is always `key=value`) could corrupt byte alignment for everything downstream - the exact mechanism behind tonight's earlier bugs. Phase 1 (`tokenize`) is now a single mechanical forward pass with zero shape assumptions: every token's width comes purely from its own 2-byte type tag against the now-complete value catalog, producing a flat, self-describing tape. Phase 2 (the section parsers - `parseCountriesSection`, `parseLocationsSection`, etc.) walks that tape by index instead of by byte offset, so a wrong assumption there can at worst misread one section's meaning - it can no longer corrupt alignment for anything after it. Consolidated the ~13 near-identical section parsers (each hand-rolling the same "peek CLOSE, resolve key, expect EQUALS, recurse into database={n={...}}" boilerplate) into two shared helpers (`walkSection`, `walkDatabase`), cutting real duplication as a direct byproduct of the migration rather than adding it. Verified against all 6 real melted-save ground-truth fixtures (versions 1.1.2/1.1.10/1.3.10, solo and 8-player) with zero field mismatches, plus both real saves from tonight's investigation, before and after - byte-for-byte identical results to the pre-rewrite parser. Found two more real, subtle bugs getting there: `0x0001`/`0x0003`/`0x0004` (EQUALS/OPEN/CLOSE) aren't *exclusively* structural control codes in this format - they're also legitimately reused as bare opaque enum values in specific fields (byte-verified in `population.database`'s `pop_demand` array and elsewhere), and the old architecture already tolerated this by falling through to its generic "unmapped token" case; the new tokenizer's stricter-by-construction value resolver had to be taught the same tolerance explicitly. Trade-off worth knowing: tokenizing the whole gamestate up front (rather than only the bytes actually visited) costs real time/memory on the biggest real save tested tonight - 274MB gamestate, ~7.8s and ~690MB peak RSS with every extraction option on, up from roughly 3-6s before. Considered acceptable for the robustness gained; typed-array tape storage and lazy string decoding (matching jomini's own zero-copy `Scalar<'a>` design more closely) are available follow-ups if this ever becomes a real bottleneck.

- **Fixed real bug: the binary parser's value-type catalog was missing 5 real Clausewitz token codes, silently truncating any save that used them.** Cross-checked our token table against [jomini](https://github.com/rakaly/jomini) - the Rust parser PDX Tools itself is built on, which lists EU5 as an officially supported game - and found `I64` (`0x0317`, 8 bytes), `F32` (`0x000d`, 4 bytes), the 3-byte and 4-byte string_lookup ref codes (`0x0d41`/`0x0d3f`, needed once string_lookup exceeds 65,536 entries - a long multiplayer campaign's easily does), and a dedicated empty-string code (`0x0d42`) had zero handling anywhere in ours. Every one of them fell through to the catch-all "unresolved token, assume zero payload bytes" default, under-consuming their real payload and desyncing every byte read afterward - the exact same mechanism already diagnosed and fixed once for `0x029c` (`U64`), just for codes no reference save had ever been large enough to exercise. All 5 are now decoded with their real widths. Root-caused and verified against a real 74-year, 8-player, 2,545-country campaign (274MB gamestate) that a `0x0317` inside its location data was silently eating: before, that save recovered only countries (2,545) and a partial location list (6,583, cut off mid-desync); after, it parses cleanly end to end with all 8 players, 15 wars, and the full 28,573-location map, with zero warnings. Also fixed alongside it: the top-level gamestate loop assumed every entry is `key=value` and silently `break`s (no error, no warning) the instant that's not true, unlike the nested walker (`skipBody`) which already tolerates bare/unkeyed array elements - the same save has a long run of anonymous `{target=... start_date=... expiration_date=...}` records (accumulated diplomatic timers a short solo game never generates enough of) sitting at the true top level right after `diplomacy_manager`, which the old loop hit and gave up on entirely. Both fixes verified not to change output at all on the existing real HUN `1337.6.1` reference save.

- **Fixed real bug: uploaded saves could silently parse to nothing, depending on which release a browser had last visited during.** `/js/*` gets a year-long immutable `Cache-Control` (netlify.toml), keyed entirely on each script's own `?v=` query string - the exact mechanism already identified and partly fixed for the top-level `index.html` `<script>` tags.   - Institution progress values now show as a percentage (e.g. `100%`) instead of a bare number; a fully-embraced institution (stored as the string `"yes"` rather than a number) no longer renders as `NaN`.
  - "Weighted Tax / 1k People" and "Total Group Tax" now carry the same `tax` unit suffix as the sibling Tax Base stat.
  - "Raw Material Capacity" now reads e.g. `1 RGO capacity` instead of a bare `1`.
- **Map: moved rendering from the CPU to the GPU (WebGL2).** Panning/zooming the map used to visibly spike CPU usage and spin up fans, even on fast machines - the old renderer recomputed every visible pixel (fill color, box-average downsampling once zoomed out, border/coastline detection, selection highlight) in a plain JS loop, on the main thread, on every single animation frame. That's now a WebGL2 fragment shader doing the same per-pixel work in parallel on the GPU instead, which is what tools like PDX Tools do too. Falls back automatically to the old CPU renderer if WebGL2 isn't available at all. Measured: drag-frame timing while fully zoomed out went from ~22-32ms average (with spikes to 400ms) to a flat 16.67ms (60fps) with no spikes.
  - Known gap: the "control" mapmode's fragmented-ownership shading pass wasn't ported yet (everything else - political, players, development, population, tax, markets, religion, culture, prosperity, trade, selection, labels, tooltips, click-through - was verified against the old renderer). Follow-up if it turns out to matter.
  - Fixed shortly after release: player/AI realm borders were rendering as a single GPU pixel, which is visually indistinguishable from the ordinary thin location-boundary line already drawn everywhere - so multiplayer nation borders looked like they'd disappeared entirely. The CPU renderer thickens this same edge into a several-pixel-wide line; the GPU version now does the same (checks a small neighborhood around each pixel for a realm change, not just the immediate neighbor), confirmed against the CPU renderer on a real multiplayer save with 8 player nations. Also fixed a real, independent bug found in the process: coastline shading was reading a location's own "is this a sea tile" flag through an inverted water check that made it always resolve to false.
- **Map: population/tax/development gradients now color by percentile rank instead of any value-based scale.** First tried a log scale (better than the original linear min→max, which crammed nearly every location into the same dark color), but a side-by-side against a PDX Tools screenshot of the same save/region showed ours still reading mostly one color - these fields stay right-skewed even in log space. Coloring by each location's *rank* among its scope's locations instead of its raw value is invariant to that skew entirely (by construction, colors always spread evenly across the full gradient, no matter how lopsided the underlying numbers are) - this is the standard "quantile classification" technique cartographers use for exactly this kind of data, and is almost certainly what PDX Tools is doing too. Confirmed a real, even green→yellow→orange→brown spread on the same region PDX Tools was screenshotted at.
- **Investigated: a specific save shows prosperity as a single flat color.** Root-caused - that save has only 3 locations (out of ~13,000+) with any recorded prosperity value at all, vs. 12,000+ for control/tax/development. Missing values currently get filled in as an explicit 0 for any owned location that has other data, so with so few real data points, everyone's identical "0" ends up anchoring one end of the whole gradient. Looks like an early-game save where prosperity genuinely hasn't diverged anywhere yet, not a parsing bug. Not yet fixed - candidate fix is falling back to "no data" gray instead of a fabricated 0 when a field's real data is this sparse.
- **Map: replaced the heat gradient with a richer multi-hue ramp** (green → olive → gold → orange → dark red-brown), matching the ColorBrewer "sequential multi-hue" family (the YlOrBr/YlOrRd style) that PDX Tools also uses for province heatmaps. The previous dark-brown → tan → green ramp read as muddy/low-contrast across the middle of the range - a single-hue ramp doesn't carry enough visually-distinct steps for a full map legend, especially with population/tax now log-scaled. Adjacent-step contrast checked with the dataviz skill's palette validator.
- Fixed shortly after release: the new multi-hue ramp above shipped with low/high reversed (green at 0, brown at the max) - the original convention was the other way around (dark at 0, green at the max, per the "floor color" note in the code). Same five colors, just flipped back to the original direction.
- **Map: heat gradient (development/population/tax/control/prosperity) recolored again, this time to dark brown → yellow → green → bright cyan-blue**, per user sign-off against a PDX Tools screenshot. The previous brown/orange/gold/olive/green ramp had a real defect independent of hue choice: measured luminance showed it peaking in brightness at the gold stop (~75% up the scale) then getting darker again for olive/green - the brightest color on the map was never the highest value. The new ramp's floor is a dark chocolate-brown rather than literal black, for the same reason as before: true black reads as identical to the page's own background/`NON_PLAYER_MUTED`, which would make a genuine 0% location indistinguishable from "nothing rendered here." Percentile-rank scaling (unchanged) still does the actual work of spreading real save data evenly across the gradient regardless of skew - confirmed with a simulated right-skewed dataset that linear scaling crowds 92% of locations into the darkest quarter of the gradient, log scaling still crowds 29%, percentile rank spreads it exactly evenly (25% in each quarter).
- **Map: heat gradient's control points are now spaced unevenly across percentile-rank space instead of evenly.** Originally: bottom 30% brown/near-black, next 25% (30-55th percentile) yellow, next 40% (55-95th) green, top 5% bright cyan-blue - a hard-edged classed/flat-band version of this was tried first (confirmed on a real save), then changed back to a smooth blend between those same anchor points per follow-up feedback, so within-band relative ranking (a 60th vs. 90th percentile location) is visible again. Re-tuned once more against a reference screenshot to compress brown/yellow into the bottom ~40% and stretch green/blue across the remaining ~60% (was ~70%/~30%) - green is now the dominant color across most of a real save's landmass, with blue visibly present rather than a rare accent. Then pulled blue back to only the true top 1% of locations (an "elite handful" flag rather than a visible band), giving the ~14 points of range that freed up to yellow (now ~29% of the range, up from ~15%) rather than green, per user request. The map legend's gradient-bar sampling was bumped from 9 to 61 points so it accurately renders a curve with unevenly-spaced control points instead of smoothing it into an evenly-spaced blend.
- **Map: removed the drag/zoom "fast" render mode** that stripped province borders and player/trade-good labels while actively panning or zooming. It was a leftover optimization from the old full-CPU renderer (skip the two most expensive passes during motion, redraw in full ~90ms after the user stops) - no longer needed now that rendering is a GPU fragment shader, so borders and labels stay on screen throughout a drag or zoom instead of flickering away and back.
- **Map: brightened the Trade Goods mapmode a little.** It was darkened from its original neon-hashed colors per earlier feedback, but ended up slightly too dark/muddy - eased the final darken step back up (was -0.16, now -0.06) while keeping the desaturation toward muted land that fixed the original neon problem.

- **Map: hiding a player now removes them from the map too**, not just the Players table/Trends/Llama Score. Their player-realm border, name label, and "Players" mapmode grouping/legend entry all disappear - their territory falls back to reading as ordinary AI/muted land. Works via a new `visiblePlayers()` filter in `js/map.js` threaded through every place the map reads a country's player-name list (there were about 10 of them), keyed off the same excluded-players Set the Hide/Show buttons already persisted to localStorage.
- **Hiding now also happens automatically when the desktop tracker's campaign ledger shows a player has actually left** - not just via the manual Hide button. New `LlamaScore.computeDepartedPlayers(snapshots)` reuses the existing per-country control timeline (already built for war-scoring's "player-departed" categorization) to find any player name that appears somewhere in the timeline but is absent from every country's LATEST known roster - i.e. genuinely gone, not just mid-move between countries (confirmed with synthetic timelines for both cases). `getAllExcludedPlayers()` (app.js) unions this with the manual list for every place a player should disappear from view (Players table, Trends, Map); the manual list itself stays untouched by auto-detection, so Hide/Show still only ever read/write an explicit user choice. Refreshes automatically the moment a campaign ledger links (or a live poll picks up new recorder data), not just on next reload. Known gap: the "Show all" button only clears the *manual* list - an auto-detected departed player stays hidden until they reappear in the ledger's own latest roster, which is intentional (nothing to "show" if the tracker still says they're gone) but worth knowing about.
